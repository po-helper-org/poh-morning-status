# poh-morning-status

Утренний бриф Product Owner одной командой: что изменилось за сутки по рабочим каналам,
какие цели стоят на спринт, что делать сегодня. Набор навыков и адаптация под
[DeepSeek Harness](https://github.com/deepseek-ai/deepseek-harness) (dsh), чтобы PO
открывал день не с обхода семи вкладок, а с одного ответа в чате.

**Функция [манифеста](https://github.com/po-helper-org/.github/blob/main/profile/README.md):**
4 — риски и раннее предупреждение. Меряется лид-таймом сигнала: сколько часов между
появлением отклонения в канале и моментом, когда PO его увидел.

**Статус:** работает в dsh. Навык `/morning` собирает отчёт из Backlog.md, рендерер
превращает его в интерактивные слайды (на узком экране — мобильную ленту), плагин
подключает всё к харнессу. Календарь и чаты — по дорожной карте ниже.

## Как проверить

```sh

cd ../tools/morning-slides && python3 -m unittest discover -s test     # рендер: 13 тестов
node test/e2e.mjs                                                       # E2E: Chromium, 6 сценариев
cd ../mts-link-sync && npm test                                         # коннектор: офлайн-тесты

```

без него — `cd tools/mts-link-sync && PLAYWRIGHT_BROWSERS_PATH=$PWD/.browsers npx playwright install chromium`.

## Ситуация

PO начинает рабочий день. Информация о вчерашнем дне размазана по MTS.Link (чаты и
созвоны), рабочему Telegram, корпоративной почте Exchange, JIRA и Confluence. Цели
спринта лежат в артефактах планирования, задачи — в личном планнере. Обход всех
источников занимает от сорока минут и делается нерегулярно, поэтому сигнал об
отклонении PO получает не утром, а на эскалации.

Нужен один вход: команда `/morning` → полная картина → подтверждённый план дня.

## Тезис: бриф — не пересказ каналов

Если собирать «всё, что произошло за вчера», получится дайджест на два экрана, который
читают десять минут и закрывают без действий. За сутки в двух десятках наблюдаемых
чатов проходят сотни сообщений; меняют день PO единицы.

Бриф показывает не «что было», а **что изменилось так, что меняет план на сегодня**.
Остальное сворачивается в одну строку `Прочее: 47 сообщений в 6 чатах, ничего
требующего внимания`. Навык, который не умеет уверенно свернуть шум, бесполезен: PO
всё равно пойдёт читать каналы руками.

Три класса сигналов проходят в бриф:

| Класс | Почему в брифе | Куда ведёт |
|---|---|---|
| **Ждут тебя** | кто-то заблокирован решением, ответом или согласованием PO | прямо в план на сегодня |
| **Сдвиг или блокер** | что-то из спринта поехало, прогноз к цели изменился | пересмотр приоритетов |
| **Факт к цели** | решение принято, зависимость снялась, KR продвинулся | обновление картины |

Всё, что не попало в три класса, существует в брифе только числом.

## Три слоя разной природы

Запрос PO выглядит однородным, но собирается тремя разными способами — и путать их
нельзя, иначе дешёвое начинает пересчитываться по цене дорогого.

| Слой | Природа | Частота пересборки | Источник |
|---|---|---|---|
| **1. Что произошло** | дельта, дорого: сеть и LLM-разбор | каждое утро | каналы |
| **2. Цели спринта** | константа, дёшево | раз в спринт | артефакт планирования |
| **3. Что делать сегодня** | решение, не список | каждое утро, с участием PO | планнер + слои 1–2 |

Слой 3 — не `task list`. Список задач планом дня не является: без привязки к цели
спринта, без ёмкости дня и без разбора просроченного он выдаёт занятость за работу.
Навык предлагает план с обоснованием каждой строки и останавливается на подтверждении.

Отдельный обязательный блок — **просроченное**. Задачи с ушедшим сроком, которые молча
едут дальше, обесценивают доску быстрее всего. Бриф раз в день заставляет их разрешить:
сделать, перенести или закрыть.

## Каналы

Часть каналов уже закрыта работающими инструментами, часть требует коннектора. Пробел
помечается в брифе явно (`[НЕТ ДАННЫХ: канал не подключён]`), а не маскируется молчанием.

| Канал | Состояние | Чем закрывается |
|---|---|---|
| **MTS.Link — чаты** | коннектор работает | `mts-link-chat-sync` (WS-API, read-only, SSO-сессия) + навыки `/chat-watch`, `/chat-sync`; классификация — `/link-radar` |
| **MTS.Link — созвоны** | коннектор работает | `/transcript-sync` → `/daily-review` (стендапы) и `/summary` (прочие) |
| **Задачи PO** | работает | Backlog.md как MCP-инструменты в dsh (`mcp__backlog__*`) |
| **Цели спринта** | частично | milestone и KR-узлы есть; зафиксированного `ПЛАН-{sprint}.md` нет — до первого прогона `sprint-planner` слой честно помечается `[ЦЕЛЬ СПРИНТА НЕ ЗАФИКСИРОВАНА]` |
| **Telegram рабочий** | коннектор нужен | Telethon user-session; рабочий образец — `export_forum_topics.py` в брендовом контуре, паттерн реестра — `mts-link-chat-sync` |
| **JIRA + Confluence** | доступ есть, в dsh не подключён | MCP-сервер `atlassian` (jira.mts.ru, Confluence MTSLIVE) настроен для Claude Code через Docker-гейтвей; нужна строка в профиле dsh |
| **Email (Exchange)** | путь известен | DavMail-гейтвей, уже проверенный на корпоративном Exchange в [poh-scheduller](https://github.com/po-helper-org/poh-scheduller) для календаря (`davmail.mode=EWS`, NTLM); там `davmail.imapPort=0` — включение IMAP-плеча даёт почту тем же способом |

Про Exchange отдельно: корпоративной регистрации приложения не будет и IMAP напрямую
закрыт, но DavMail уже работает на этом сервере под VPN. Это делает почту не
исследовательской задачей, а конфигурационной.

## Архитектура: тонкий оркестратор

`/morning` не собирает данные сам. Он вызывает существующие навыки и складывает их
вывод в один ответ. Дублировать логику разбора чатов внутри брифа нельзя — появятся две
расходящиеся реализации, и через месяц они начнут давать разные ответы на один вопрос.

```
/morning
  ├─ проверка свежести дампов ──▶ /chat-sync, /tg-sync   (только если устарели)
  ├─ слой 1: дельта за сутки ───▶ /link-radar (окно = сутки, все каналы)
  │                              + JIRA/Confluence через MCP atlassian
  ├─ слой 2: цели спринта ──────▶ артефакт планирования + KR-узлы (чтение)
  ├─ слой 3: план дня ──────────▶ Backlog.md + дельта слоя 1
  └─ STOP: подтверждение PO ────▶ запись в планнер (dry-run → approve)
```

**Дельта-курсор.** Без состояния «до какого места уже видел» бриф каждое утро покажет
те же блокеры. Курсор хранит по каждому каналу метку последнего разобранного момента и
список сигналов, которые PO видел и не закрыл: они переезжают в «висит на тебе», а не
показываются как новые. Приём взят из `/daily-review`, где carry-forward берётся из
открытых задач планнера, а не из папки.

**Свежесть вместо демона.** Запуск ручной, поэтому выгрузка на старте означала бы
ожидание. Навык сначала смотрит на возраст дампов: свежие — сразу анализ; старше
порога — предлагает обновить с оценкой времени. Ночной таймер можно добавить позже как
оптимизацию; на архитектуру он не влияет.

**Право записи.** Навык меняет планнер только после явного подтверждения: показывает
dry-run (закрыть, перенести срок, создать задачу из сигнала) и ждёт. Без права записи
бриф описывает цикл, но не закрывает его.

## Принципы

- **Каждый факт ← источник.** Сигнал без якоря (канал, автор, время) в бриф не попадает.
  Нет источника — `[УТОЧНИТЬ]`, не догадка.
- **Пробел виден.** Неподключённый канал помечается явно. Молчание канала и его
  отсутствие — разные вещи, и путать их нельзя.
- **Read-only на источниках.** Коннекторы только читают: не отправляют сообщений и не
  помечают прочитанным, чтобы не сбивать счётчики непрочитанного у PO.
- **Свёртка обязательна.** Шум сворачивается в число. Бриф, который вырос до двух
  экранов, свою функцию не выполнил.
- **Оркестратор не дублирует сборщиков.** Логика разбора живёт в профильных навыках.

## Дорожная карта

| Шаг | Что | Зависимости |
|---|---|---|
| 1 | `tools/telegram-sync` — Telethon user-session, реестр наблюдаемых чатов, окно `--days N`, выгрузка в markdown с `purpose`/`extract` во frontmatter | свой `api_id`/`api_hash` с my.telegram.org |
| 2 | Навыки `/tg-watch` и `/tg-sync` — зеркало пары `/chat-watch` + `/chat-sync` | шаг 1 |
| 3 | Расширение `/link-radar`: чтение дампов обоих мессенджеров, окно в сутки | шаг 2 |
| 4 | Навык `/morning` — оркестратор, курсор, STOP-гейт | шаг 3 |
| 5 | Подключение `atlassian` MCP в профиль dsh — JIRA и Confluence в брифе | Docker-гейтвей, VPN |
| 6 | Email-плечо DavMail (IMAP) + выгрузка окна писем | развёртывание рядом с poh-scheduller |
| 7 | Календарь как ограничение ёмкости дня | синк из poh-scheduller |

Шаги 1–4 дают работающий бриф на двух мессенджерах и планнере. Шаги 5–7 расширяют охват,
не меняя конструкцию.

## Границы

**В объёме:** утренний бриф, дельта по каналам, план дня с подтверждением, запись
результата в планнер.

**Вне объёма:** планирование спринта (`sprint-planner`), разбор дейликов
(`/daily-review`), генерация требований (`poh-bft-writer`), двусторонняя синхронизация с
трекерами. Навык эти артефакты читает и на них ссылается, но не производит.

**За человеком остаётся:** приоритет при конфликте целей, решение по каждой просроченной
задаче, оценка реалистичности плана дня.

## Установка

**dsh** — плагин [`poh-morning-plugin/`](poh-morning-plugin/README.md): подключает `skills/`
как отдельный провайдер навыков харнесса и добавляет правило маршрутизации, по которому
«план на сегодня» / «morning» поднимают навык `/morning`. Пошагово — в README плагина.
Отчёт открывается в панели dsh как мобильная лента; тот же файл на широком экране —
слайды для руководителя.

**Claude Code и другие IDE-агенты** — по конвенции контура PO: `install.sh` с выбором агента
синкает `skills/` в нужный корень (не реализовано).
