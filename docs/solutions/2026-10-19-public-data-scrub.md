# В публичном репозитории оказались реальные данные корпоративного контура

## Ситуация

Аудит организации 2026-10-18, категория A: публичный репозиторий утреннего отчёта содержал
реальные данные корпоративного контура. Фамилии коллег (в том числе хендлы), ключ проекта
в трекере задач, название корпоративного чата, адрес трекера, ключ пространства вики,
домен харнесса, локальный путь пользователя — в коде, тестовых фикстурах и документации.

## Причина

Репозиторий вырос из внутреннего инструмента: фикстуры тестов копировали реальные выгрузки,
а имена людей, ключи проектов и хосты зашивались прямо в код — в том числе ключ конкретного
проекта в регулярке подсветки ссылок на задачи в `tools/morning-slides/render.py`.

## Решение

Все реальные значения заменены на вымышленные (12 файлов с кодом и фикстурами плюс
README и docs). Тонкое место — `render.py`: регулярка `ID_RE` подсвечивала только вшитый
ключ одного проекта. Наивная замена значений в фикстурах либо ломала подсветку, либо
оставляла имя проекта в коде. Поэтому регулярку генерализовали: подсвечивается любой ключ
трекера вида `[A-Z][A-Z0-9]+-\d+`, без имени проекта в коде. Заодно добавлена лицензия
CC BY-SA 4.0 (выбор владельца, текст из GitHub Licenses API) и раздел о лицензии в README.

## Как проверить

Юнит-тесты трёх инструментов после замены зелёные (14 + 9 + 29 OK, Python 3.12);
e2e-прогон не запускался — правки в нём те же замены имён, что покрыты тестами рендера.
Контрольный `git grep` по прежним фамилиям, ключам, внутренним доменам и локальным путям —
пусто.

## Уроки

История git старые значения сохраняет — скраб ветки её не чистит; переписывание истории
и смена видимости репозитория — отдельное решение владельца, а не часть такого PR.
Регулярки с вшитыми ключами и хостами при обезличивании надо генерализовать, а не менять
значение: иначе имя проекта остаётся в коде или ломается функциональность. Репозиторий,
выросший из внутреннего инструмента, требует аудита на реальные данные до открытия.
