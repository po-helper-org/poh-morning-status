# Навык: выгрузка чатов MTS.Link

Обёртка над `tools/mts-link-sync/`. Ты качаешь сырые сообщения за окно в markdown;
разбор содержимого — отдельная работа поверх скачанных файлов, под `purpose`/`extract`
каждого чата.

> Роль: **диспетчер выгрузки чатов PO**. Не анализируешь содержание внутри этого навыка —
> отдаёшь файлы и честно отчитываешься, что выгружено и чего не хватает.

## Границы

- **НЕ** анализирует сигналы — это `/link-radar` поверх готовых дампов.
- **НЕ** разбирает транскрипты созвонов — это `/summary` и `/daily-review`.
- **НЕ** логинится сам: корпоративный SSO проходит только PO.
- **НЕ** пишет в чаты и не помечает прочитанным.

## Константы окружения

```yaml
tool_dir:  "<repo>/tools/mts-link-sync"          # poh-morning-status
config:    "<tool_dir>/.env"                     # MTS_LINK_OUTPUT_DIR обязателен
dumps:     "GROUND/_intake/chats/"               # из MTS_LINK_OUTPUT_DIR
registry:  "<dumps>/watched-chats.yaml"
cursor:    "<dumps>/.sync-cursor.json"
session:   "~/.mts-link-chat-sync/auth.json"     # SSO-секрет: не читать, не коммитить
```

## Шаг 0 — всегда начинай со `--status`

```bash
cd <tool_dir> && npm run status
```

Офлайн, без сети. Печатает: есть ли SSO-сессия, куда пишутся выгрузки, найден ли реестр,
сколько чатов под наблюдением, насколько свеж курсор. **Код выхода 1 — есть незакрытая
проблема**, читай блок «Проблемы» и действуй по нему, не переходи к выгрузке.

Это не формальность. Предшественник этого инструмента при пропавшем конфиге сообщал
«реестр пуст» и выходил с кодом 0 — то есть отчитывался о спокойном дне в день, когда всё
горело. `--status` существует, чтобы такое расхождение было видно до выгрузки.

## Шаг 1 — выгрузка

Окно выбирается по задаче, не по привычке:

| Ситуация | Команда |
|---|---|
| Утренний бриф, регулярный прогон | `node sync.mjs --pull --since-last` |
| Нужен конкретный вчерашний день | `node sync.mjs --pull --yesterday` |
| «за неделю» / «за месяц» | `node sync.mjs --pull --days 7` / `--days 30` |
| Явные даты | `node sync.mjs --pull --from ГГГГ-ММ-ДД --to ГГГГ-ММ-ДД` |
| Посмотреть, что выгрузилось бы | добавь `--dry` |
| Все чаты минуя реестр | добавь `--all` (purpose/extract будут пустыми) |

`--since-last` — режим брифа: берёт окно от метки последнего выгруженного сообщения по
каждому чату. Без него каждый прогон переваливает одно и то же, и PO приучается
пролистывать повторы.

`--yesterday` — ровно предыдущие календарные сутки по МСК. Не заменяй его на `--days 1`:
скользящее окно, запущенное утром, срежет вчерашний вечер пополам, а там чаще всего и
принимают решения, меняющие план.

Результат: по файлу на чат `<окно> <название>.md`. Frontmatter несёт `chat-id`, `window`,
`purpose`, `extract`, `msg-count`, `incremental`. Пустые чаты пропускаются — в выводе они
видны строкой «нового нет».

## Шаг 2 — отчёт PO

Коротко: сколько файлов, за какое окно, перечислить чаты с числом сообщений. Отдельно
назвать чаты, где нового не было. Затем предложить разбор — для каждого файла читается
`purpose`/`extract` из frontmatter и вытаскивается именно то, что там просят. Сам разбор
запускай по просьбе PO, не молча.

## Настройка наблюдаемых чатов

```bash
node sync.mjs --list-chats                    # нумерованный список
node sync.mjs --list-chats --search продукт   # на 1000+ чатов — фильтруй
node sync.mjs --watch 0,3,7                   # показать chat-id выбранных
node sync.mjs --add --chat-id "<id>" --name "<название>" \
  --purpose "<зачем слежу>" --extract "<что вытаскивать>"
node sync.mjs --list-watched
node sync.mjs --unwatch "<chat-id>"
```

**Не выбирай чаты за PO.** Показал список — PO называет номера. На каждый выбранный
спроси двумя вопросами: `purpose` (зачем следишь) и `extract` (что вытаскивать). Эти поля
направляют последующий анализ; пустые превращают дамп в стену текста без приоритета.

`--add` идемпотентен по `chat-id`, повтор не плодит дублей.

## Диагностика отказов

| Симптом | Что это | Действие |
|---|---|---|
| `MTS_LINK_OUTPUT_DIR не задан` | нет `.env` | скопировать `.env.example` → `.env`, указать путь до `GROUND/_intake/chats` |
| `Нет SSO-сессии` | не было входа | СТОП, PO делает `npm run login` |
| `Session expired — redirected to login` | сессия протухла | СТОП, PO делает `npm run login` заново |
| `Could not capture the chat WS token` | сменился протокол или не открылся сокет | СТОП, сообщить PO; чинится в инструменте, не обходится |
| `Реестр пуст` при существующем файле | расхождение путей | прогнать `--status`, сверить `MTS_LINK_OUTPUT_DIR` |

Протухшая сессия — **всегда СТОП**. Не пытайся логиниться скриптово: SSO проходит только
PO, а попытка автоматизации ломает сессию.

## Guardrails

- **Read-only.** Инструмент шлёт только `token`, `ping` и `Get*`. Никогда не добавляй
  мутирующие вызовы (`Chat.MarkMessagesAsRead` и подобные) — они сбросят счётчики
  непрочитанного у PO.
- **`auth.json` не читать, не печатать, не коммитить.**
- **Скачанные `.md` не править построчно.** Перенос и переименование — файловой операцией.
- **Не выдумывать содержание.** Нет дампа — нет фактов; сообщи, что выгрузки нет.
- **Курсор не трогать руками.** Если нужно перевыгрузить окно — используй явные
  `--from/--to`, они игнорируют метку в большую сторону.
