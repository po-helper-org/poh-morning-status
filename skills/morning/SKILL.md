# Навык: утренний отчёт PO

> Роль: **дежурный по утру**. Собираешь состояние из Backlog.md и отдаёшь PO одну
> картину: что горит, что ждёт решения, что делать сегодня. Сам ничего не решаешь и
> не меняешь — план дня предлагаешь, PO подтверждает.

Срабатывает на `/morning`, слово `morning`, «план на сегодня», «утренний отчёт»,
«что на сегодня», «с чего начать». Аргументы не нужны.

## Границы

- **Единственный источник — Backlog.md** через инструменты `mcp__backlog__*`
  (`task_list`, `task_view`, `milestone_list`, `task_search`). Нет инструментов —
  запасной путь: `backlog task list … --plain` через терминал. Нет ни того, ни
  другого — так и сказать: `[НЕТ ДАННЫХ: Backlog.md недоступен]`, отчёт не выдумывать.
- **Не читает чаты и транскрипты** — это `/mts-link-sync` и `/link-radar`. Если PO
  просит «что нового в чатах» — направить туда, в отчёт не подмешивать.
- **Не пишет в Backlog.md** внутри отчёта. Изменения (закрыть, перенести срок,
  завести задачу) — только после явного «да» PO на конкретный пункт, по одному.
- **Не пересказывает доску.** Полный список задач планом не является; в отчёт
  попадает то, что меняет день, остальное — числом.

## Модель данных (что где лежит)

| Сущность | Как хранится в Backlog.md | Как читать |
|---|---|---|
| Цель квартала (Objective) | milestone `m-N` | `milestone_list` |
| Ключевой результат (KR) | задача `type: okr`, привязана к milestone | `task_list` с `type: ["okr"]` |
| Задача PO | `type: potask`, метка `okr-kind:task` | `task_list` с `type: ["potask"]`, `labels: ["okr-kind:task"]` |
| Договорённость | `type: potask`, метка `okr-kind:control` | то же с `labels: ["okr-kind:control"]` |
| Риск | `type: potask`, метка `okr-kind:risk` | то же с `labels: ["okr-kind:risk"]` |
| Требование (БФТ) | `type: bft`, стадия — статус (`FAST-DONE` → `REVIEW-DONE` → `DEEP-WORK` → `DEEP-REVIEW` → `DEEP-DONE`) | `task_list` с `type: ["bft"]` |
| Привязка к KR | метка `okr-kr:<id>` на задаче | видна в `task_view` |
| Срок | `dueDate`, в списке печатается `(due ГГГГ-ММ-ДД)` | сравнить с сегодняшней датой |

Задача без `okr-kind:*` — тоже задача (kind `task` по умолчанию). Задача без
`okr-kr:*` — общая, к цели не привязана; это валидно, не считать ошибкой.

## Шаг 1 — сбор (ровно эти вызовы, не больше)

Сегодняшняя дата: если она есть в контексте — взять оттуда; если нет — один вызов
`date +%F` в терминале, и только он. Без даты «просрочено» и «сегодня» не считаются.

1. `milestone_list` — цели и прогресс `сделано/всего`.
2. `task_list` `type: ["okr"]` — все KR со статусами.
3. `task_list` `type: ["potask"]` — все задачи PO одним списком (kind виден только
   через метки, поэтому дальше три узких вызова).
4. `task_list` `type: ["potask"]`, `labels: ["okr-kind:control"]` — договорённости.
5. `task_list` `type: ["potask"]`, `labels: ["okr-kind:risk"]` — риски.
6. `task_list` `type: ["potask"]`, `labels: ["okr-kind:risk"]`, `unassigned: true` —
   риски без владельца. Владелец отдельным вызовом на каждый риск не проверяется.
7. `task_list` `type: ["bft"]` — требования по стадиям.

Задачи (`okr-kind:task` и без метки) = список 3 минус списки 4 и 5.

Списки печатаются группами по статусу; `Done` и `Cancelled` в отчёт не идут.
Блок «закрыто со вчера» без `--json` недоступен — опускается, не выдумывать.

`task_view` — только для пунктов, попавших в «Просрочено» и «Сегодня», и не больше
6 штук: нужны привязка к KR и суть. Риски, договорённости, KR, БФТ через `task_view`
не смотреть — строки списка достаточно. KR по целям: если нужен состав milestone —
`task_list` с `milestone: "<id>"`, по одному вызову на цель, не больше.

Бюджет: около 10 вызовов инструментов на отчёт. Больше — значит, отчёт собирается
не по этому навыку.

## Шаг 2 — классификация

Каждую открытую задачу отнести ровно к одному блоку, в этом порядке приоритета:

1. **Просрочено** — `due < сегодня`, статус не `Done`/`Cancelled`. Любой kind.
2. **Сегодня** — `due == сегодня`.
3. **Риски** — `okr-kind:risk`, открытые. Отдельно пометить риск **без владельца**
   (нет assignee) — это открытый вопрос, не управляемый риск.
4. **Договорённости** — `okr-kind:control`. Ближайшие 7 дней — по датам, остальные —
   числом.
5. **Ближайшая неделя** — задачи с `due` в пределах 7 дней.
6. **Прочее** — всё остальное открытое: только число, по kind.

Требования (БФТ) идут отдельным блоком: по стадиям, с выделением тех, у кого есть
`due` в пределах недели или просрочен.

Цели: по каждому milestone — прогресс из `milestone_list` и список KR со статусом.
KR в `In Progress` — «в работе», в `To Do` без единой привязанной задачи — пометить
`[KR без задач]`: это цель, по которой ничего не движется.

## Шаг 3 — отчёт

Формат — строго этот, заголовки не переименовывать, пустой блок — одна строка
«нет». Ссылки на задачи — по id (`PO-105`), без путей к файлам.

```
## Утро {ГГГГ-ММ-ДД}

### 🔴 Просрочено ({n})
- PO-99 · Сетевая доступность для GDS · был срок 2026-09-10 (−1 д) · KR PO-78
  → решить сегодня: сделать / перенести / закрыть

### 🎯 Сегодня ({n})
- PO-105 · Ишманов + Бордюг: отправить смету за август · KR PO-78

### ⚠️ Риски ({n}, без владельца: {k})
- PO-112 · Вебхук по заказам не работает, ломается CJM у VK · KR PO-78 · [без владельца]

### 🤝 Договорённости ({n}, на неделе: {k})
- PO-104 · Юмшанов: перепроверить вебхук заказов · до 2026-09-16

### 📋 Требования (БФТ): {n} · FAST-DONE {a} · REVIEW-DONE {b} · DEEP-WORK {c} · DEEP-REVIEW {d}
- PO-97 · Взаиморасчёты ВК за август · до 2026-09-20 · To Do  ← горит

### 🧭 Цели квартала
- m-1 Objective 1 · 0/9
  - PO-36 Доля отказов на оплате ниже 2% · To Do
  - PO-42 … · To Do · [KR без задач]
- m-2 …

### Прочее
Задач {n}, договорённостей {m}, рисков {r} — без сроков на неделе, внимания не требуют.

### План на сегодня (предложение)
1. PO-105 — срок сегодня, KR PO-78.
2. PO-99 — просрочен на день, решить судьбу.
3. PO-112 — риск без владельца: назначить или закрыть.

Подтверди план или скажи, что убрать/добавить. Изменения в Backlog.md внесу только
после твоего «да» по пункту.
```

Правила блоков:

- Каждый пункт — `id · суть · срок/дельта · KR` в одну строку. Второй строкой — только
  действие для просроченного.
- В «План на сегодня» — не больше 5 пунктов, по одному основанию на строку: срок,
  просрочка, риск без владельца, блокирующая договорённость. Ёмкость дня PO —
  не пять «в работе» одновременно, список из 12 пунктов планом не является.
- Если просроченных больше 5 — показать 5 самых старых, остальные числом, и первым
  пунктом плана предложить разбор просроченного целиком.
- Числа в заголовках — реальные счётчики из данных, не оценки.

## Шаг 4 — STOP и запись

После отчёта — остановиться. Изменения делать только по явному подтверждению PO и
только через инструменты Backlog.md (`task_edit`, `task_create`, `task_complete`),
по одному пункту, с показом того, что именно изменится, до вызова:

| PO говорит | Действие |
|---|---|
| «PO-99 сделано» | `task_edit` → `status: Done` |
| «PO-99 перенести на пятницу» | `task_edit` → `dueDate: <дата>` |
| «PO-112 на Юмшанова» | `task_edit` → `assignee` |
| «заведи задачу …» | `task_create` с `type: potask`, метка `okr-kind:<kind>`, при наличии KR — `okr-kr:<id>`, срок `--due` |

Новые задачи — только `type: potask` (панель «Управление целями» читает строго его),
не `task` и не `bft`.

После записи — одной строкой, что изменилось, и напомнить нажать «Обновить» в
разделе «Управление целями»: панель не следит за фоновыми правками.

## Guardrails

- **Нет источника — нет факта.** Backlog.md недоступен → `[НЕТ ДАННЫХ]`, а не
  «спокойный день».
- **Не округлять и не сглаживать.** Просроченное на 20 дней так и называется, а
  не «немного затянулось».
- **Не менять Backlog.md без «да».** Даже очевидное («срок вчера, задача явно
  сделана») — сначала вопрос.
- **Не звать `/mts-link-sync` и другие навыки** из этого отчёта. Слой каналов —
  отдельный запрос PO.
