# mts-link-sync

Выгружает сообщения отслеживаемых чатов МТС Линк (`my.mts-link.ru/chats/`) в markdown —
источник данных для утреннего брифа. Адаптация `mts-link-chat-sync` из
`ishmanov-cortex/tools/` под нужды `/morning`: добавлен дельта-курсор, режим суточного
окна и офлайн-диагностика.

> **Строго read-only.** Инструмент только читает: логинится под сохранённой сессией и
> запрашивает историю. Он никогда не отправляет сообщения и **не помечает прочитанным** —
> счётчики непрочитанного у PO не сбиваются. Клиент физически шлёт только `token`, `ping`
> и `Get*`-запросы (`wsClient.mjs`).

## Как это работает

Публичного API у МТС Линк нет. Чат работает по JSON-RPC поверх WebSocket. Доступ гибридный:

1. `harvest.mjs` — Playwright один раз открывает `/chats/` под сохранённой SSO-сессией и
   снимает из хендшейка WS-токен, URL сокета и `organizationId`.
2. `wsClient.mjs` — Node открывает свой WebSocket с этим токеном и вызывает RPC напрямую.
   Браузер во время самой выгрузки не нужен.

## Требования

- Node.js ≥ 21 (нужны `process.loadEnvFile` и глобальный `WebSocket`).
- Доступ к МТС Линк через корпоративный SSO.

## Установка

```bash
npm install                     # playwright + yaml
npm run browser                 # скачать Chromium — только если его ещё нет
cp .env.example .env            # ОБЯЗАТЕЛЬНО: указать MTS_LINK_OUTPUT_DIR
npm run login                   # разовый вход через SSO, сохранит сессию
npm run status                  # проверить, что всё на месте
```

Загрузка Chromium вынесена из `postinstall` в отдельный `npm run browser`: под
ограниченными правами `playwright install` падает с `EPERM` на системном кэше
`~/Library/Caches/ms-playwright` и роняет всю установку.

Если системный кэш недоступен или его чистят — ставь браузер рядом с инструментом:

```bash
PLAYWRIGHT_BROWSERS_PATH=$PWD/.browsers npx playwright install chromium
```

и пропиши в `.env`:

```
PLAYWRIGHT_BROWSERS_PATH=/абсолютный/путь/tools/mts-link-sync/.browsers
```

Проверить, какой бинарь будет использован:

```bash
node -e "import('./harvest.mjs').then(()=>console.log(require('playwright').chromium.executablePath()))"
```

Проверять надо именно так, через `harvest.mjs`. Playwright читает
`PLAYWRIGHT_BROWSERS_PATH` один раз при вычислении модуля, а ESM поднимает все
`import` наверх — поэтому `config.mjs` (он грузит `.env`) импортируется в
`harvest.mjs` и `login.mjs` **первым**. Прямой `require('playwright')` покажет
системный путь и соврёт.

## Почему `MTS_LINK_OUTPUT_DIR` обязателен

У предшественника этот путь имел дефолт — папку внутри самого инструмента. Когда `.env`
с реальным путём до волта пропал, инструмент продолжил завершаться с кодом 0, читая пустой
реестр не оттуда и создавая рядом пустую папку. Сообщение «реестр пуст» невозможно было
отличить от «ты смотришь не в ту директорию».

Для утреннего брифа это худший из возможных отказов: он молча отчитается о спокойном дне
в день, когда всё горело. Поэтому дефолта нет, а `--status` возвращает ненулевой код при
любой незакрытой проблеме.

## Использование

### Диагностика (без сети)

```bash
npm run status
```
Печатает: есть ли SSO-сессия и сколько ей дней, куда пишутся выгрузки, найден ли реестр,
сколько чатов под наблюдением, насколько свеж курсор. Код выхода 1 при незакрытой проблеме.

**Возраст сессии — предупреждение, а не вердикт.** Корпоративный SSO истекает на сервере, и
файл на диске до и после выглядит одинаково: доказать можно только сетевым вызовом. Поэтому
старая сессия не блокирует запуск, но и не выдаётся за исправную — иначе `--status` отвечает
«Всё на месте» про сессию, мёртвую две недели.

### Настройка наблюдаемых чатов

```bash
node sync.mjs --list-chats                      # нумерованный список (на 1000+ чатов — с --search)
node sync.mjs --list-chats --search продукт
node sync.mjs --watch 0,3,7                     # показать chat-id выбранных
node sync.mjs --add --chat-id "<id>" --name "<название>" \
  --purpose "<зачем слежу>" --extract "<что вытаскивать>"
node sync.mjs --list-watched
node sync.mjs --unwatch "<chat-id>"
```

`purpose` и `extract` — свободный текст: зачем PO следит за чатом и что оттуда вытаскивать.
Они уезжают во frontmatter каждого файла и направляют последующий анализ, чтобы бриф
доставал важное для PO, а не пересказывал всё подряд.

### Выгрузка

```bash
node sync.mjs --pull --since-last     # инкрементально от курсора — режим брифа
node sync.mjs --pull --yesterday      # ровно вчерашний день по МСК
node sync.mjs --pull --days 7
node sync.mjs --pull --from 2026-09-01 --to 2026-09-03
node sync.mjs --pull --since-last --dry   # показать, что выгрузилось бы
node sync.mjs --pull --all --days 1       # все чаты минуя реестр
```

Пишет по файлу на чат: `<окно> <название чата>.md`. Frontmatter: `type`, `chat-id`,
`window`, `purpose`, `extract`, `msg-count`, `incremental`, `source`. Тело — реплики
`Автор ЧЧ:ММ: текст`, сгруппированные по дням. Пустые чаты пропускаются.

## Дельта-курсор

`.sync-cursor.json` рядом с выгрузками хранит по каждому чату метку самого свежего уже
выгруженного сообщения.

Без курсора каждый прогон переваливает одно и то же окно: радар заново классифицирует те же
блокеры, и к концу первой недели PO приучается их пролистывать — ровно тот отказ, который
делает ежедневный бриф бесполезным.

Решения, заложенные в реализацию:

- **Метка — время сообщения, а не время запуска.** Настенные часы молча потеряли бы
  сообщения, пришедшие во время самой выгрузки.
- **Окно начинается на миллисекунду позже метки.** Диапазон API включающий: старт ровно с
  метки повторял бы последнее сообщение каждый раз, и каждый дамп открывался бы строкой,
  которую PO уже читал.
- **Метка только растёт.** Прогон по старому окну не откатывает курсор и не вызывает
  повторных выгрузок.
- **Есть пол в 7 дней.** Возвращение из двухнедельного отпуска даёт вчерашний бриф, а не
  перечитывание трёх тысяч сообщений, которое похоронит сигнал.
- **Курсор пишется после файлов.** Падение на середине оставляет метку позади: будет
  безвредная повторная выгрузка, но не молчаливый пропуск.
- **Битый курсор считается отсутствующим.** Деградация в «выгрузи запрошенное окно», а не
  падение и не пропуск.

## Разработка

```bash
npm test        # 29 тестов, без сети
```

Тесты покрывают курсор (монотонность, пол, деградация), границы окна (`--yesterday` через
полночь и через границу месяца, МСК-рендеринг) и диагностику конфигурации (каждый вид
поломки виден, исправная не даёт ложных тревог). Всё, что требует сети, вынесено из
тестируемых модулей: `window.mjs` и `cursor.mjs` — чистые.

Тесты конфигурации запускаются в дочернем процессе с `MTS_LINK_ENV_FILE`, указывающим в
несуществующий файл. Без этой изоляции локальный `.env` разработчика подхватывался бы и
кейсы проходили бы по неверной причине, перестав ловить ту самую поломку.

## Отношение к `ishmanov-cortex/tools/mts-link-chat-sync`

Этот инструмент — преемник. Формат реестра `watched-chats.yaml` и формат дампов
совместимы, существующий реестр и 149 уже выгруженных файлов продолжают работать.

Различия: обязательный `MTS_LINK_OUTPUT_DIR`, префикс переменных `MTS_LINK_*` вместо
`CHAT_SYNC_*`, режимы `--status`, `--since-last`, `--yesterday`, поле `incremental` во
frontmatter, тесты.

Пока оба существуют, источником истины считается этот. Порядок вывода предшественника из
эксплуатации — в `docs/migration-from-cortex.md`.
